# moye — Self-Evolving AI Agent Built on rig

[English](./README.md) | [简体中文](./README.zh-CN.md)

A self-evolving autonomous-loop AI Agent built on [rig](https://github.com/0xPlaygrounds/rig) (Rust LLM framework). Features multi-provider, multi-model support, Human-in-the-Loop (HITL) gating, a skill system, and self-evolution.

---

## The Name: Moye (莫邪)

> In the Spring and Autumn period, the swordsmith Gan Jiang was ordered by the King of Wu to forge a pair of legendary swords. The iron in the furnace would not melt — the fire was not hot enough. His wife, Mo Ye, climbed onto the furnace wall and cast herself into the flames. The sacrifice broke the spell. The iron melted, and two swords were born: *Gan Jiang* and *Mo Ye* — the sharpest blades of their age.

A sword must pass through fire to be born. An AI agent is no different — it must iterate, evolve, and remake itself to become truly useful. Moye is built on this belief: **transformation is the only path to sharpness**. The agent reads its own code, learns from every task, and rewrites its own prompts — not because it is broken, but because standing still is not enough. What does not transform, does not survive.

### Dependency Direction

The domain layer (`agent_loop`, `registry`, `reviewer`, `prompt_evolve`) depends only on `event` and `config` modules, never on `ui`. The config module parses `agent.toml` once, shared crate-wide via `Arc<Config>` or `config::config()`. The presentation layer (`ui::tui`) depends on `event` and its own submodules. This ensures dependency inversion: adding a CLI/API consumer requires no domain-layer changes.

### Core Concepts

| Concept | Description |
|------|------|
| **Autonomous Loop** | User inputs a goal, Builder plans and calls tools autonomously, stops at max_turns or task completion. |
| **SDD Pipeline** | Implementation intent auto-routes through the Investigator to Planner to Builder to Auditor pipeline. |
| **Human-in-the-Loop** | Tool calls gated by `allow / ask / deny` tiers; dangerous operations pause for human confirmation. |
| **Multi-Role** | Orchestrator / Investigator / Planner / Builder / Auditor. |
| **Self-Evolution** | Prompt evolution + code evolution + tool extension, improving through accumulated experience. |
| **Skill System** | Runtime-loaded Markdown skill files injected into prompts, no recompilation needed. |
| **Event-Driven** | Agent output flows to TUI via `AgentEvent` channel, decoupling domain from presentation. |
| **Filesystem Sandbox** | Agent can only access the project root and subdirs by default; accessing other directories requires manual user authorization. |
| **Web Tools** | Built-in `web_fetch` (fetch & strip HTML) and `web_search` (DuckDuckGo), permission-tiered per role. |
| **Model History** | Used models persisted to `~/.config/moye/models.json`; the `/models` picker lists recently used for one-tap switching. |
| **Sandbox Providers** | OS-level sandbox selected at startup via `[sandbox].mode`: `auto` probes bwrap, `landlock` is the LSM fallback, `off` disables. Injected as a `SandboxProvider` seam trait. |
| **Tool Pipeline** | 3-stage execution: pre/post `PipelineHooks` + `TimeoutRetryTool` around-execute wrapper, composed by rig's `HitlHook`. |
| **Waterfall Events** | Lifecycle events (AgentPreStep / ToolsPreExecute / ToolsPostExecute / AgentTurnStopping) dispatched to emit / waterfall / serial listeners. |
| **Profile System** | Declarative config overlays (`[profile.<name>]` patches) applied at parse time; `--dump-config` inspects the resolved tree. |

## Provider Configuration

Set `AGENT_PROVIDER` to select a provider. API keys are read from provider-specific environment variables. All providers use the OpenAI-compatible interface. Five providers are supported: DeepSeek, Bailian (DashScope), Moonshot (Kimi), Volcengine (Ark), and Custom.

### Recommended: `.env` file

The program auto-loads a `.env` file from the project root at startup (if present), so you configure once and every launch picks it up. No manual export needed. Explicitly exported variables take precedence and are never overridden.

```bash
# First-time setup: copy the template and fill in your key
cp .env.example .env
# Edit .env: set AGENT_PROVIDER and the corresponding API Key
# Available providers: deepseek / bailian / moonshot / volcengine / custom

cargo run   # Auto-loaded on every subsequent launch
```

`.env` is gitignored; secrets never enter git.

## Filesystem Sandbox

The Agent can only access the **project root (current working directory) and its subdirectories** by default. Access to other directories pauses and prompts the user for authorization.

### How It Works

| Step | Behavior |
|------|------|
| 1. Tool call | Sandbox checks the path before execution when Agent calls `read_file` / `edit_file` / `write_file` / `run_bash` |
| 2. Path inside sandbox | Silent pass-through, execution continues |
| 3. Path outside sandbox | HITL prompt appears, asking user to authorize |
| 4. User confirms | Directory added to allow-list, no future prompts |
| 5. User denies | Tool call skipped, Agent receives rejection reason |

### Detected Path Patterns

The sandbox extracts these path patterns from `run_bash` commands:

- Absolute paths (`/etc/passwd`)
- Home-directory paths (`~/.config`)
- Relative paths with `..` (may escape sandbox)
- `cd` / `pushd` target arguments
- Redirection targets (`> /tmp/file`)

### Disabling the Sandbox

```bash
# Disable via env var (not recommended)
export AGENT_SANDBOX=off
cargo run
```

> **Security note**: With the sandbox disabled, the Agent can access any path on the filesystem. Use only in trusted environments.

## Tool Permissions (HITL Gating)

Each role's tool calls are gated by three permission tiers:

| Tier | Behavior | Typical Scenario |
|------|------|----------|
| `allow` | Silent execution, no prompt | `read_file`, `run_bash` (read-only commands like `ls`, `git status`), `web_fetch`, `web_search` |
| `ask` | Pause, ask yes/no | `run_bash` (dangerous commands like `rm`), Builder's `edit_file` |
| `deny` | Blocked, not executed | Planner/Auditor's `edit_file`, `run_bash_mutating`, Auditor's `web_fetch`/`web_search` |

> Tool classification is automatic via `is_readonly_bash()`. Read-only commands (`ls`, `cat`, `git log`, etc.) are classified as `run_bash_readonly`; everything else as `run_bash_mutating`. `web_fetch` and `web_search` also have their own permission fields, defaulting to `ask`.

## Sandbox Providers

Beyond the path-checking filesystem sandbox, moye selects an OS-level sandbox provider at startup based on `[sandbox].mode`. The provider is built once and injected as a `Box<dyn SandboxProvider>` seam trait, so backends are swappable without touching tool code.

| Mode | Provider | Isolation | When to use |
|------|------|------|------|
| `auto` (default) | `SimpleSandbox` | Probes for the strongest available backend (bwrap mount namespace, then seatbelt, then path-only) | Recommended for most setups |
| `bwrap` | `SimpleSandbox` | Explicit bwrap backend | When you want bwrap and want startup to fail if it is unavailable |
| `landlock` | `LandlockSandbox` | Linux Landlock LSM path-level access control (no mount namespace; weaker than bwrap) | Linux 5.13+ without bwrap |
| `off` / `false` / `0` | `SimpleSandbox` (disabled) | No OS-level isolation | Trusted environments only |

`LandlockSandbox` is a fallback, not a co-equal provider. Its `probe()` returns `Full` when bwrap is available (bwrap wins), `Partial` when only Landlock is available, and `Unusable` when neither is present. Selection is fail-closed: with `mode = "landlock"` and no Landlock kernel support and no bwrap, the provider returns `Unusable` and commands are not executed.

Pre-authorized directories (`[sandbox].authorized_dirs`) skip the HITL prompt for both the path-checking sandbox and the OS-level provider.

## Tool Pipeline

Tool execution runs through a 3-stage pipeline composed on top of rig 0.41's `AgentHook` before/after callbacks. Two independent layers keep concerns separated:

| Layer | Mechanism | Purpose |
|------|------|------|
| Pre/post hooks | `PipelineHooks` (`Vec<Box<dyn Fn>>` listeners) | Run before/after each tool call; map to rig's `ToolCallAction` / `ToolResultAction` |
| Around-execute | `TimeoutRetryTool<I: Tool>` wraps `inner.call()` | `tokio::time::timeout` per call, plus retry on timeout (no retry on inner errors) |

**Pre-execute actions** (`PreAction`): `Run` (proceed), `Skip(reason)` (deny and return the reason to the model), `Rewrite(args)` (replace arguments, then proceed). The last listener's verdict wins.

**Post-execute actions** (`PostAction`): `Keep` (pass through), `Rewrite(content)` (replace what the model sees), `Stop` (halt the agent loop). The first non-`Keep` action short-circuits.

The `Pipeline` orchestrator composes `pre_execute` -> approval (`ApprovalChain`) -> `execute` (`TimeoutRetryTool`) -> `post_execute` into a testable unit. In production, rig's runtime already wires these stages through `HitlHook::on_tool_call` / `on_tool_result`.

## Waterfall Events

A thread-safe `WaterfallRegistry` dispatches lifecycle events on top of rig 0.41's hook callbacks. Three listener kinds cover different needs:

| Kind | Dispatch | Can short-circuit? | Typical use |
|------|------|------|------|
| `emit` | Fire-and-forget; all listeners run | No | Logging, `SessionLog` |
| `waterfall` | Sequential; each gets `(event, next)` | Yes, skip `next()` to halt | Pre/post tool stages |
| `serial` | `await` each in order | No (observe-only async) | Async listeners (SDD roles) |

**Events** (`WaterfallEvent`): `AgentPreStep` (role + goal), `AgentRequest` (message), `ToolsPreExecute` (tool + args), `ToolsPostExecute` (tool + result + ok), `AgentTurnStopping` (reason). Only `ToolsPreExecute` and `ToolsPostExecute` are waterfall-eligible.

**Actions** (`WaterfallAction`): `Continue` (call `next()` to delegate down the chain) or `ShortCircuit` (return without calling `next()`; later listeners don't run). An empty chain returns `Continue`.

## SDD Pipeline with Listeners

The Investigator, Planner, and Auditor are registered as serial listeners on the `WaterfallRegistry` instead of being called as a hard-coded sequence. `run_autonomous()` dispatches `AgentPreStep` with the role and goal; the listeners read and write a shared `PreStepState` (investigation, plan, goal override, escape flag, error) to coordinate the pipeline.

| Listener | Triggered on | Writes to shared state |
|------|------|------|
| Investigator | `AgentPreStep` (Builder role) | `investigation`, or sets `escape` when no investigation is needed |
| Planner | `AgentPreStep`, after the Investigator | `plan` |
| Auditor | `AgentTurnStopping` | `AuditState.verdict` (Approve / Reject / Clarify) |

**Fast mode**: when the active profile is named `fast` (`[profile.fast]` or `AGENT_PROFILE=fast`), `run_sdd_pipeline` skips investigation, planning, and audit entirely and runs the Builder directly. This is the quick-task path; the default profile keeps the full SDD discipline.

## Profile System

Profiles are declarative config overlays applied on top of the base `agent.toml` at parse time. A profile is an ordered list of patches; each patch locates a path in the config tree via `id` (dot-separated) and replaces its entire value with `config` (a TOML inline table). There is no deep merge, the whole value at the `id` is swapped.

Selection precedence: `AGENT_PROFILE` env var > `[profile].active` field > none (backward-compatible, base config unchanged).

```toml
[profile]
active = "fast"

[profile.fast]
name = "fast"
patches = [
  { id = "agent", config = { default_model = "deepseek-v4-flash", max_turns = 5 } },
  { id = "sandbox", config = { mode = "landlock", authorized_dirs = [] } },
]

# Profiles can chain via `base` (base's patches apply first, then this profile's):
# [profile.strict]
# name = "strict"
# base = "fast"
# patches = [ { id = "agents.auditor.permissions", config = { edit_file = "deny" } } ]
```

Inspect the resolved config (base + profile overlay) with the `--dump-config` CLI flag, which prints the combined tree as TOML with a leading `# Active profile: <name>` comment when a profile is selected. A patch whose `id` doesn't exist in the base config errors out (fail-closed), as does selecting an unknown profile name.

## Context Management

Long-running agent sessions accumulate conversation history (user messages, assistant replies, tool call results) that eventually exceeds the model's context window. moye uses a **two-tier progressive compaction strategy** that automatically manages context without losing critical information.

### Strategy Overview

```
                    estimated tokens
                         │
           ┌─────────────┴─────────────┐
           │                           │
     ≤ microcompact_threshold    > microcompact_threshold
           │                           │
     Continue                      Tier 1: Microcompact (no LLM)
                                    │
                           ┌────────┴────────┐
                           │                  │
                     Still overflow       Below threshold
                           │                  │
                     Tier 2: LLM Summarization    Return microcompacted
                           │
                     Return summary + recent
```

| Tier | Mechanism | Trigger | LLM Call | Cost |
|------|------|------|------|------|
| **Tier 1 — Microcompact** | Scans old `ToolResult` entries in history, protects the last N, replaces older tool results with `[Tool result cleared]` marker | Estimated tokens > `microcompact_threshold` (default 20000) | No | Minimal (in-memory) |
| **Tier 2 — LLM Summarization** | Sends old conversation history to a summarization LLM, generates a 5-section anchored summary, replaces with a single System message | Still exceeds `compaction_threshold` after Tier 1 (default 0.5 x effective budget) | Yes | Moderate (one LLM call) |

### Tier 1: Microcompact

A lightweight compaction **without an LLM call**. Tool call results (`ToolResult`) typically consume many tokens (e.g., `read_file` returning hundreds of lines, `run_bash` returning long output), but their full content is often no longer needed in subsequent turns.

**Workflow:**

1. Scan all `ToolResult` positions in history
2. Protect the last `microcompact_protected_results` (default 3)
3. Replace older `ToolResult` content with `[Tool result cleared]`
4. Preserve `id` and `call_id` (needed by the API for tool call correlation)

**Example:**

```
Before:
  User: do task 1
  Assistant: [tool_call: read_file]
  User: [ToolResult: fn main() { ... 200 lines of code ... }]   ← cleared
  Assistant: [tool_call: run_bash]
  User: [ToolResult: cargo build output ... 50 lines ...]       ← cleared
  Assistant: [tool_call: edit_file]
  User: [ToolResult: file edited successfully]                  ← kept (one of last 3)
  Assistant: [tool_call: run_bash]
  User: [ToolResult: cargo test output ... 30 lines ...]        ← kept
  Assistant: [tool_call: read_file]
  User: [ToolResult: fn helper() { ... }]                       ← kept

After:
  User: do task 1
  Assistant: [tool_call: read_file]
  User: [ToolResult: [Tool result cleared]]                     ← replaced
  Assistant: [tool_call: run_bash]
  User: [ToolResult: [Tool result cleared]]                     ← replaced
  Assistant: [tool_call: edit_file]
  User: [ToolResult: file edited successfully]                  ← kept as-is
  ...
```

### Tier 2: LLM Summarization

Triggered when tokens still exceed `compaction_threshold` after Tier 1. Sends old conversation history to a summarization LLM, generating a **5-section anchored summary** (inspired by OpenCode) to ensure critical information is preserved. If a previous summary exists in history, the LLM updates it incrementally rather than creating from scratch.

**5-Section Summary Template:**

| # | Section | Content |
|---|------|------|
| 1 | Objective | User's goal (1-2 sentences) |
| 2 | Important Details | Constraints, decisions, key facts |
| 3 | Work State | Completed / Active / Blocked — work status |
| 4 | Next Move | What needs to happen next |
| 5 | Relevant Files | File paths and why they matter |

**Compacted History Structure:**

```
[System: [Conversation Summary]
  ## 1. Objective ...
  ## 2. Important Details ...
  ...
  ## 5. Relevant Files ...]
[System: Continue if you have next steps ...]
[User: recent turn 1 message]          ← keep_recent_turns retained
[Assistant: recent turn 1 reply]
[User: recent turn 2 message]
...
```

### rig PatchRequest Mechanism

Compaction uses rig's `Flow::PatchRequest` + `RequestPatch::history()`. This is a **per-turn non-sticky** replacement: it only modifies the history sent to the API for the current turn, without affecting rig's internally persisted real transcript. This means the Agent always has access to the full real history, but uses the compacted version when sending to the API.

### Configuration Parameters

All parameters are configured in the `[context]` section of `agent.toml`:

| Parameter | Default | Description |
|------|------|------|
| `max_output_tokens` | `0` | 0 = skip `max_tokens` (use model's default output budget; reasoning models always skip); >0 = explicit cap sent to non-reasoning models (must not exceed the target model's output ceiling, or 400). Not used in the context-budget calc. |
| `compaction_threshold` | `0.5` | Tier 2 trigger ratio (fraction of effective budget, 0.0-1.0) |
| `keep_recent_turns` | `2` | Recent turns kept during Tier 2 compaction |
| `max_bash_output_chars` | `20000` | Max chars for `run_bash` output |
| `max_read_lines` | `500` | Max lines for `read_file` output |
| `microcompact_threshold` | `20000` | Tier 1 trigger token threshold |
| `microcompact_protected_results` | `3` | Number of recent tool results protected during Tier 1 |

> **Effective Budget** = `context window × 0.85` (a fixed 15% reserve for model output; `max_output_tokens` is NOT used here). E.g., 128K window → effective budget 108,800 tokens, Tier 2 trigger = 108,800 × 0.5 = 54,400 tokens.

### Caching

Compaction results are cached (`compaction_cache`). When the history length hasn't changed (e.g., the Agent enters `handle_completion_call` multiple times while waiting for user input), the last compaction result is reused directly, avoiding redundant computation.

## Skill System

Skills are runtime-loaded Markdown files automatically injected into agent prompts.

```bash
# Add a skill
> add-skill rust-expert "Rust idioms, unsafe safety, lifetime optimization"
> add-skill code-reviewer "Code review: security, correctness, maintainability"

# List registered skills
> skills
- rust-expert
- code-reviewer
```

Skill files are stored in `skills/` as `skills/<name>.md` with detailed instructions. The Agent scans and injects relevant skills into prompts at startup.

## Logging

Logging is file-only (no terminal output in TUI mode):

```
logs/2025-07-25_14-30-00.log
```

Log level: `info` (default), `rig_core=off` (suppress rig internal logs to avoid SSE span flooding).

To adjust log level, modify `EnvFilter` in `src/main.rs`:

```rust
// info and above only
tracing_subscriber::EnvFilter::new("info")

// Include rig HTTP debug (verbose, debug only)
tracing_subscriber::EnvFilter::new("info,rig_core=trace")

// Suppress rig internal logs (default)
tracing_subscriber::EnvFilter::new("info,rig_core=off")
```
